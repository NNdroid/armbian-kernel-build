## P0 — 必然出错或已埋下复发炸弹

### P0-1 `opts_y+=(...)` 绕过 mode 去重，与 200 行注释自相矛盾
`userpatches/extensions/kernel-inject.sh:1188`

```bash
opts_y+=(NET INET PROC_FS CRYPTO NETFILTER IPV6 NET_SCHED NET_SCH_FQ)
```

同一文件 `:518-528` 用 11 行注释郑重说明"**单纯 append 到 opts_y 不足以覆盖早先的 opts_m 声明**，必须先移除冲突声明"，并为此实现了 `_kernel_inject_force_mode`（`:48-77`，内部逐个 `_kernel_inject_array_remove` 清理 `opts_n/opts_y/opts_m`）。

但 `:1188` 这行**裸 `+=`**，恰好是注释里点名禁止的写法。而这 8 个符号并非无关紧要：`NET`、`INET`、`NETFILTER`、`IPV6` 都在 `_kernel_inject_full_network_y_options`（`:141-147`）里被正确地走 force_mode，`NET_SCHED`、`NET_FQ` 也是。若 Armbian 的 family config 对其中任何一个有 `opts_m` 声明，`:1188` 的裸追加与之并存时，最终 `.config` 里就是 `=m`，随后 `:758` 的 `_kernel_inject_verify_symbol_list "${config_file}" y required_y` 会失败 —— 表现为"构建 1 小时后在校验阶段炸"，且原因极难定位。

**修复**：改为
```bash
for symbol in NET INET PROC_FS CRYPTO NETFILTER IPV6 NET_SCHED NET_SCH_FQ; do
    _kernel_inject_add_mode "${symbol}" y || return 1
done
```

### P0-2 `TARGET_SERIES` 硬锁 `7.2`，上游一升版整个 hk1box 目标静默瘫痪
`userpatches/config/build-targets/hk1box.conf:11` + `scripts/lib/targets.sh:50`

```bash
TARGET_BRANCHES=(edge)
TARGET_SERIES=([edge]=7.2)
```

`targets.sh:50` 会用这个值做**硬校验**：`validate_target_series`（`:83-90`）一旦 `CONFIG_KERNEL_VER != 7.2` 就直接 `return 1`，`pipeline.sh:48` 随即中止。而 `meson64_common.inc` 的 `edge` 版本会随时间推进（`rockchip64` 侧的 `current/edge/bleedingedge` 已经是 6.18/7.2/7.3）。

于是：上游 edge 一旦从 7.2 走到 7.3，**整个 hk1box 目标彻底无法构建**，错误信息只有一行 `[ERROR] hk1box / edge requires kernel series 7.2, got 7.3` —— 不提示"请更新 profile"。

同时 `scripts/package_hk1box.sh:71` 和 `:140` 又各自独立硬编码了版本：
```bash
[[ "${branch}" == edge && "${version}" == 7.2.* && -f "${marker}" ]] || return 1   # :71
[[ "${release}" =~ ^7\.2\.[0-9]+-[-A-Za-z0-9._+]+$ ]] || return 1                    # :140
```
四处版本约束散在三个文件，改一处忘三处。

**修复**：把版本常量收敛到 profile 的单一来源，`package_hk1box.sh` 从环境/profile 读取而非硬编码；`validate_target_series` 的报错信息补上"上游已推进，请同步 profile"的指引。

### P0-3 `local -A TARGET_SERIES=()` 让 profile 的 series 声明被静默丢弃
`userpatches/config/boards/hk1box.conf:24-25`

```bash
local -A TARGET_SERIES=()          # 声明为函数局部变量
source "${USERPATCHES_PATH}/config/build-targets/hk1box.conf"
```

`source` 进来的 `TARGET_SERIES=([edge]=7.2)` 会**优先解析到已声明的 local 变量**，于是 profile 里那条 series 约束在这条路径上完全失效。目前因为该函数只用 `TARGET_REQUIRED_Y`（`:31`、`:39`），没暴露；但任何人日后在此引用 `TARGET_SERIES` 都会拿到空值，且不会有任何报错。

**修复**：直接删掉 `local -A TARGET_SERIES=()`，profile 已 `declare -ga` 了。

### P0-4 release 上传 glob 会把 hk1box 的 bundle 漏掉/错配
`scripts/lib/pipeline.sh:133`

```bash
"./build/output/debs/*-${branch}-${BUILD_FAMILY}_*__${BUILT_KERNEL_VER}-*.deb"
```

这是硬编码的 `.deb` 形态。而 hk1box 走 `ophub-tar` adapter，真实交付物是 `build/output/hk1box/<uname-r>.tar.gz`（`package_hk1box.sh:98`）。`release.sh:25` 会 `compgen -G` 这个 glob 拿到 deb 列表，再由 `target_extra_release_assets`（`adapters/ophub-tar.sh:14-23`）追加 tar.gz。

问题在于 `:42-45`：只要 deb 列表非空就允许发布。也就是说 **tar.gz 生成失败（`package_hk1box.sh` 返回非 0）时，流程在 `pipeline.sh:124` 就 return 了**，倒不会发半成品；但一旦未来有人放宽调用顺序，或者 deb 存在而 tar 不存在，`release.sh` 会静默发出一个没有安装包的 Release。这个"两类交付物必须同时存在"的约束目前**没有任何地方断言**。

**修复**：在 `pipeline.sh:124` 之后、`upload` 之前，加一条 adapter 级的完整性断言（`target_extra_release_assets` 返回空即失败）。

## P1 — 应当修复

### P1-1 `hmac.compare_digest` 遇非 ASCII 头抛 TypeError，且在 try 之外
`scripts/live_log_server.py:150`（调用点 `:741`，`try` 从 `:743` 才开始）

`self.headers.get()` 返回 latin-1 解码的 str。实测：
```
hmac.compare_digest('Basic \xff\xfe', 'Basic YWJj...')
TypeError: comparing strings with non-ASCII characters is not supported
```
任何人发一个 `Authorization: Basic \x80` 即稳定触发 500 + 栈打到 stderr。

**修复**：两侧都编码成 bytes 再比。
```python
supplied = self.headers.get("Authorization", "").encode("latin-1", "replace")
if hmac.compare_digest(supplied, self.server.expected_authorization):
    return True
```

### P1-2 日志脱敏用 `read(64K)`，实时流被硬生生延迟 64 KiB
`scripts/redact_log_stream.py:87` 和 `:94`

`sys.stdin.buffer.read(n)` 在管道上**阻塞直到攒满 n 字节或 EOF**。这直接击穿"实时日志"这个核心卖点：build.sh 早期输出稀疏时，用户会看到日志卡住不动，甚至构建快结束才一次性刷出。

**修复**：两处改用 `read1`（语义等价但不等满缓冲）。
```python
while chunk := sys.stdin.buffer.read1(64 * 1024):
```

### P1-3 `skipped_symbols` 这条兼容路径零测试覆盖
`tests/test_kernel_injection.sh:345-346` 把 `DEBUG_INFO_NONE`/`DEBUG_INFO_REDUCED` 人为写进 fixture 的 Kconfig，于是 `kernel-inject.sh:695-702` 那条"符号在树中未定义 → 记入 skipped 并跳过校验"的分支永远走不到。全文件 grep `skipped_symbols` 零命中。

这恰好是记忆中"内核升级后符号被移除"的核心防御机制 —— 唯一有价值的测试却没测。

**修复**：删掉那两行 fixture 定义，补一条 `assert_array_contains _kernel_inject_skipped_symbols DEBUG_INFO_NONE`。

### P1-4 `KERNEL_INJECT_MISSING_SYMBOLS` 成功路径不清空，测试断言会被残留满足
`kernel-inject.sh:657-659` 只在**失败**时赋值。`tests/test_kernel_injection.sh:373/382/395/406` 的 `grep` 断言因此可能被上一次失败留下的条目满足 → **假通过**。

**修复**：verify 前 `KERNEL_INJECT_MISSING_SYMBOLS=()`；测试里也显式 reset。

### P1-5 发布失败回退分支零覆盖，对应真实的"半成品 Release"风险
`tests/test_kernel_injection.sh:489-501` 的 `gh()` mock 恒返回 0，导致 `release.sh:80-96` 里 `gh release create` 失败后的 `view`/`edit`/`upload --clobber` 分支一行都没跑过。

而这条分支本身有真实风险：`release.sh:87-90` 先 `gh release edit` 改 notes（此时 Release 已存在），再 `upload --clobber`。若 upload 失败，就留下一个**有 notes 没 deb** 的空 Release。

**修复**：给 mock 加 `GH_MODE` 开关，至少覆盖 `create_fails` 与 `view_fails` 两条路径。

### P1-6 `pre_package_kernel_image` 钩子的派发路径零覆盖
`tests/test_armbian_extensions.sh:37` 只 `declare -F` 检查函数存在（`:30`），从不真正调用。而这条路径正是产出 `defined-symbols.txt` / `source-manifest.env` 的地方 —— 整个证据链的起点。

### P1-7 `test_hk1box.py:275-305` 名字承诺 arm64/gzip 格式，实际只断言参数字符串
`mkinitramfs`/`mkimage` 桩只 `printf` 参数然后造 0 字节文件，断言的是 `"mkinitramfs -c gzip -o "` 这种字符串。`package_hk1box.sh` 若把 `-c gzip` 写成 `-c none`，测试照绿。

**修复**：让桩真的产出字节，Python 侧校验 magic：`blob[:2] == b"\x1f\x8b"`（gzip）、`blob[:4] == b"\x27\x19\x05\x96"`（uImage）。

### P1-8 测试继承宿主全部环境变量，泄漏检查的边界窗口被污染
`tests/test_redact_log_stream.py:17-18` 用 `os.environ.copy()`。`redact_log_stream.py:92` 的 `keep_bytes = max(len(value) ...)` 会被 CI 里的 `ACTIONS_RUNTIME_TOKEN` 等**无关长 token** 抬高，使 40/60 行精心构造的 64 KiB 边界窗口不再对应被测 secret —— 安全断言被削弱。

**修复**：白名单环境 `{"PATH":..., "HOME":...}` + 注入额外 secret。

### P1-9 CI 未 pin 上游 `extensions.sh`，且无 `timeout-minutes`
`.github/workflows/build-and-upload.yml:102-104` 用浮动分支 `armbian/build/main/lib/functions/general/extensions.sh` 拉契约，上游重构会让 `test_armbian_extensions.sh` 的断言失效且失效方向不可控。全文件无 `timeout-minutes`，内核编译被默认 360 分钟硬杀。

**修复**：pin 到具体 SHA 存进变量；job 级加 `timeout-minutes: 360`。

## 结论

**工程质量评价：高于同类开源项目的平均水准。** 供应链安全（pin 到 40 位 SHA 并校验）、证据链设计（从 linux-image deb 里取证据而非依赖临时工作树）、失败即停的严格性、路径逃逸防护，都做得相当扎实。`live_log_server.py` 的路径白名单和 `redact_log_stream.py` 的分片安全前缀算法（跨块、临界切分）经复核是**正确**的，不要动。

**最需要立刻处理的是 P0-1**（一行 `+=` 与 200 行注释矛盾，后果是构建一小时后失败）和 **P0-2**（四处散落的硬编码版本，上游一升版目标静默瘫痪）。**P1-3/P1-4/P1-5/P1-6** 集中反映同一个问题：证据链的**入口和出口都测到了，中间的失败分支一条都没测**，导致这些回归测试存在假通过风险 —— 这比缺测试更危险。

建议修复顺序：P0-1 → P0-2/P0-3/P0-4 → P1-1/P1-2（一行到两行，立即见效）→ P1-3..P1-8（补测试覆盖）→ P2。
